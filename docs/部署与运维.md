# 部署与运维

这份手册写的是**别人照着做能跑起来**的最小路径：拓扑、首次部署、开通一个人、日常开关、
升级与回滚，以及会让人误判"她不主动"的那些陷阱。

- [`runtime/docs/浪潮决策引擎_上线记录与回滚手册_20261002.md`](../runtime/docs/浪潮决策引擎_上线记录与回滚手册_20261002.md) —— 「浪潮」线上事故与决策记录

## 1. 拓扑：什么跑在哪里

```
QQ ── NapCat(OneBot v11) ── AstrBot ──┬── 宿主侧薄插件 astrbot_plugin_companion_runtime
                                       │        （只做注入/渲染/发送，不持有任何认知状态）
                                       └── HTTP 协议 v1 ──► Runtime fleet（一台容器，N 个进程）
                                                              ├─ 监督进程 runtime_fleet.py（控制面 :8800）
                                                              ├─ 每人一个 companion-runtime serve（:8787 起）
                                                              └─ PostgreSQL：每人一个 schema
```

要记住的四件事：

1. **两个人是两个进程、两个 schema**。机械投影（memory/candidates/outbox）没有租户键，
   多人共用 schema 会互相污染。schema 名由 `scripts/fleet_naming.py` 从会话推出：
   `default:FriendMessage:10001` → `cr_default_friendmessage_10001`。
2. **`conversation_id` 必须等于会话的 `unified_msg_origin`**。配错的表现不是报错，而是
   "角色永远不主动"或"消息投给了别人"。
3. **权威是数据库里的 CAS 指针，不是配置**。开/关主动外发用 `dispatch_authority.py`，
   改配置不生效。
4. **`AstrBot/` 零修改**，所有集成走公开 API（注入用临时 TextPart、渲染用当前聊天模型）。

## 2. 需要什么

| | |
|---|---|
| 系统 | Linux + Docker（compose v2） |
| 数据库 | **PostgreSQL 18**。运行时存储是 **PostgreSQL-only**：不给 `CR_STORAGE__DSN` 会直接拒绝启动（SQLite 只被离线 v1 导入器支持） |
| 宿主 | AstrBot 4.28.x（上游，零修改） |
| 平台 | OneBot v11 前端（作者用 NapCat） |
| 两个仓库 | 主仓库 + `astrbot_plugin_companion_runtime`（**必须克隆到主仓库根目录下、且保持这个目录名**，compose 会挂载它） |

`CR_SEMANTIC_API_KEY` 等密钥**只从环境读**，不要写进任何仓库文件。

## 3. 首次部署

```bash
git clone https://github.com/bomomoQWQ/xiaojiujiu.git
cd xiaojiujiu
git clone https://github.com/bomomoQWQ/astrbot_plugin_companion_runtime.git
```

在栈目录（本部署是 `/srv/companion/astrbot_test`，你自己的随意）里：

```bash
# 1) 数据库口令：只放这里，别进仓库
mkdir -p .secrets
cat > .secrets/runtime-v2-postgres.env <<'EOF'
POSTGRES_USER=runtime
POSTGRES_PASSWORD=<自己生成一个>
POSTGRES_DB=companion
EOF

# 2) 构建 Runtime 镜像（Dockerfile 会把 runtime/src 装成 companion_runtime 包）
docker build -t xiaojiujiu-runtime:v2-test .

# 3) 生成 fleet 的 compose（人员名单、端口、语言等服务定义都从它来）
#    路径默认就是当前目录；--project 必填——它给整套 compose 命名，猜错会挂到别人的栈上。
python scripts/build_runtime_fleet.py --people 10001,10002 --project <项目名>

# 4) 起整套
docker compose -p <项目名> -f astrbot.yml -f fleet-v2.yml up -d
```

> ⚠️ **生成器不会写 `CR_SEMANTIC_API_KEY`**。若你把它直接写进 `fleet-v2.yml` 的
> `environment:`（本部署历史上就是手工加的），**重跑生成器会把它抹掉**——表现是深层刷新
> 静默退化成"没有 provider"。正确做法是把它放进 `.secrets/` 的 env 文件、或生成器的模板里。

起完自检：

```bash
docker exec xxj-runtime-fleet python /fleet/fleet_admin.py list
```

`list` 会打印每个 scope 的端口、健康、**运行时是否允许它主动发消息**（`may send`）、
是否在 live 白名单里，以及它该用的 schema 名。

## 4. 开通一个人

```bash
docker exec xxj-runtime-fleet python /fleet/fleet_admin.py add default:FriendMessage:10003
```

`add` 不只登记，它**验证**：

1. 会话格式像不像 `unified_msg_origin`（不像就直接拒绝，因为配错的表现是"消息投错会话"）；
2. 经控制面 provision：分配端口、从会话推出 schema、写人员名单、起子进程；
3. 等健康（最多 120 秒，起不来会告诉你去 `/data/logs/<slug>.log` 看）；
4. **断言 schema 真的迁移到本构建期望的版本**（现在是 v26）。少了这一步，
   就会得到"Runtime 健康但行写进了没人读的 schema"。

最后它会提示：**新 scope 还不在 `CR_LANGCHAO__LIVE_SCOPE_ALLOWLIST` 里，所以「浪潮」live
不会为它发送**。把这个会话加进 `fleet-v2.yml` 的该变量并重建 fleet 容器即可。

体检：

```bash
docker exec xxj-runtime-fleet python /fleet/fleet_admin.py check default:FriendMessage:10003
```

`check` 逐条说明"她为什么不说话"，把每一种可能都点出来：没有 runtime 服务这个会话 /
运行时不允许主动 / 不在 live 白名单 / 权威被冻结 / schema 缺失或版本落后 / 有卡住的行。
最后给一句结论。

## 5. 日常运维

全部在 fleet 容器里跑（控制面、DSN、脚本都在容器内）。**用下面这个函数形式**，
不要写 `RT="docker exec -i ... python /fleet"` 那种——它有两个坑（§8 第 8、9 条），
复制粘贴就会坏：

```bash
RT() { docker exec xxj-runtime-fleet python "/fleet/$1" "${@:2}"; }

RT fleet_admin.py list                  # 谁在服务、能不能发
RT fleet_admin.py routes                # 会话 → Runtime URL（插件注册表用的映射）
RT fleet_admin.py check [scope]         # 体检；省略 scope 即全部
RT dispatch_authority.py show           # 每个 scope 的权威指针

RT dispatch_authority.py freeze "维护窗口"     # 立刻停止主动外发（秒级，不重启任何进程）
RT dispatch_authority.py shadow "观察"         # 继续推演/重建契约，但不外发
RT dispatch_authority.py restore "恢复"        # 交回「浪潮」live

RT rolling_restart.py                   # 干跑：只打印计划
RT rolling_restart.py --confirm         # 逐 scope 滚动：冻结→等排空→重启→健康→schema→恢复
RT rolling_restart.py --confirm --leave shadow   # 滚完先留在影子模式
```

> `fleet_admin.py` / `fleet_roster.py` / `fleet_naming.py` 是后加的工具。**服务器上的
> checkout 若还没更新，`/fleet/` 里就没有这三个文件**，`RT fleet_admin.py list` 会报
> `can't open file`。它们是每次现调的，放进去**不需要重启任何东西**
> （2026-10-07 手工放到 `…/src/xiaojiujiu/scripts/`，放完上面的命令全部实测通过）。

- **scope 名单不再写死在脚本里**：优先 `--scopes a,b`，其次 `CR_LANGCHAO_SCOPES`，
  再次监督进程的人员名单，最后控制面。**一个都拿不到时会明确拒绝**并列出试过的来源——
  照猜的名单操作会冻结/滚动错的人。
- `freeze` 与 `restore` 都不重启 AstrBot / NapCat / fleet，普通对话全程不受影响。
- `rolling_restart` 一次只动一个 scope，失败即停在那个人身上（fail-closed），后面的不动。

## 6. 升级

### 6.1 正统：重建镜像并重建容器

```bash
cd <栈目录>
git -C <主仓库> pull --ff-only          # 或切到你自己的版本
docker build -t xiaojiujiu-runtime:v2-test .
docker compose -p <项目名> -f astrbot.yml -f fleet-v2.yml up -d --force-recreate runtime-fleet
```

代价：**所有 scope 同时中断**几十秒（重启期间插件 fail-open，普通对话不受影响，主动消息会等下一轮）。

### 6.2 无中断：只换包 + 逐 scope 滚动

镜像里代码是 `pip install` 到 site-packages 的，所以"换代码"= 换那个目录，不用重建镜像：

```bash
# 在 checkout 里把 runtime/src 打成一个包
tar czf /tmp/runtime-src.tgz -C <主仓库>/runtime src

# 送进容器（docker exec 读的是【容器】的 /tmp，不是宿主机的——这里踩过）
docker cp /tmp/runtime-src.tgz xxj-runtime-fleet:/tmp/runtime-src.tgz

docker exec -u root xxj-runtime-fleet sh -c '
  rm -rf /tmp/newpkg && mkdir -p /tmp/newpkg && tar xzf /tmp/runtime-src.tgz -C /tmp/newpkg
  SP=/usr/local/lib/python3.12/site-packages
  rm -rf $SP/companion_runtime.prev
  mv $SP/companion_runtime $SP/companion_runtime.prev      # 留一份用于回滚
  cp -a /tmp/newpkg/src/companion_runtime $SP/companion_runtime
  chown -R root:root $SP/companion_runtime'

# 先确认装进去的确实是你要的版本，再滚
docker exec xxj-runtime-fleet python -c "import companion_runtime, pathlib; print(companion_runtime.__file__)"

docker exec xxj-runtime-fleet python /fleet/rolling_restart.py --confirm
```

只有 `scripts/` 是只读挂载进容器的（`/fleet`），**代码不在挂载里**——所以"改了仓库里的
`runtime/src` 却没重建镜像/没换包"时，容器跑的还是旧代码。

## 7. 回滚

| 场景 | 动作 |
|---|---|
| 刚换包，行为不对 | `SP=/usr/local/lib/python3.12/site-packages; rm -rf $SP/companion_runtime && mv $SP/companion_runtime.prev $SP/companion_runtime`，再 `rolling_restart.py --confirm` |
| 只想让主动消息闭嘴 | `dispatch_authority.py freeze "回滚中"`（秒级，不重启） |
| 镜像级回滚 | 重新 `docker build` 上一个版本，或 `docker compose ... up -d --force-recreate runtime-fleet` |
| 插件回滚 | 插件目录在 AstrBot 容器里：`/AstrBot/data/plugins/astrbot_plugin_companion_runtime`，换回旧版后**重启 AstrBot**（`docker restart astrbot-test`；NapCat 不用动） |

**插件改动必须重载 AstrBot 才生效**（插件只在启动时加载）。重载前确认没有在途动作：

```bash
docker exec xxj-runtime-fleet python /fleet/fleet_admin.py check   # 看有没有 pending/leased
```

## 8. 陷阱清单（都踩过）

1. **宿主机 `/tmp` vs 容器 `/tmp`**：`docker exec` 读的是容器里的文件。往宿主机传了包、
   却在容器里解包——装进去的是上一次的旧包，而"验证"又是在宿主机上做的，于是看起来一切正常。
   **发之前先校验产物本身**（哈希 / 关键标记），别只校验"我以为我发了"。
2. **改了仓库代码 ≠ 线上代码变了**：见 §6.2 最后一句。
3. **`rolling_restart` 不带 `--confirm` 只干跑**；它曾因为缺参数解析把 `--help` 当成执行，
   整个舰队在凌晨被滚了一遍。
4. **`in_flight_count`**：切换权威时会从持久状态重新推导在途工作，**不接受调用方少报**。
   有在途动作时切换会被拒——先等排空，这是设计。
5. **配错 `conversation_id` / 不在 live 白名单 / 权威被冻结**——三种都表现为"她不主动"。
   先跑 `fleet_admin.py check`，不要凭感觉查代码。
6. **迁移只追加**：schema 版本落后会让新代码拒绝启动（"database contains unknown future
   migrations" 是反过来的情况：库比代码新）。`check` 会直接告诉你版本号。
7. **端口只绑回环**。Runtime 没有面向公网的鉴权设计，别把它暴露出去。
8. **`RT="docker exec -i xxj-runtime-fleet python /fleet"` 然后 `$RT fleet_admin.py list`
   是坏的**：bash 按空格分词，实际执行的是 `python /fleet fleet_admin.py list`，python 把
   `/fleet` 当脚本，报 `can't find '__main__' module in '/fleet'`。用 §5 的函数形式。
9. **`docker exec -i` 会抢 stdin**：用 `bash -s`（`ssh 主机 'bash -s' < x.sh`、
   paramiko 的 `bash -s`）送脚本时，容器会把脚本**剩下的内容**读走——第一节打印完，
   后面的命令全都不执行，而且**退出码是 0**，看起来像"跑完了，一切正常"。
   交互式敲命令时 `-i` 无害；写进脚本就别带。（这个坑让一份四节的验证脚本只跑了第一节。）
10. **别把 Windows 工作区直接打包传到 Linux**：本机 `core.autocrlf=true`，`git archive`
    和资源管理器压缩产出的都是 CRLF，`.sh` 到 Linux 上会以 `\r: command not found` 失败。
    要 LF 就用 `git -c core.autocrlf=false archive`（那才是仓库里存的那份）。
    `.py` / `.json` 容忍 CRLF，`.sh` 不容忍。
11. **别用 `git checkout` 去"对齐"部署目录**——2026-10-07 差点因此把线上插件降级。
    服务器上那个插件 checkout 停在 `9baa69b`，`git status` 报 4 个文件 `M`。容器里
    `core.autocrlf` 未设，CRLF 对 LF 会把**整个文件**显示成改写，于是看起来"只是换行差异"。
    实际上 4 个里 **2 个是真内容差异**（`main.py`、`outbox.py` 里是手工放进去的热修），
    另 2 个（`settings.py`、`astrbot_executor.py`）才真是换行——**`git status` 分不出来**，
    整文件 diff 也分不出来（真差异被换行噪音淹了）。而且**容器连不上 GitHub**
    （`Failed to connect to github.com port 443`），`checkout` 之后没有 git 途径找回，
    只能靠动手前的字节级备份。部署目录里的手工改动，**先 `cp -a` 备份字节再动**。

## 9. 版本：怎么知道自己在跑什么

**一个号、四处同步**：`CHANGELOG.md` 顶部、`runtime/pyproject.toml`、
`runtime/src/companion_runtime/__init__.py`（就是 `/health` 报的 `runtime_version`）、
插件仓库的 `metadata.yaml`。改完在仓库根目录跑一次，不一致就退出码 1：

```bash
python3 scripts/check_versions.py
```

**线上跑的是哪个版本要问进程，不能看仓库**——代码在镜像和挂载里，`git pull` 不会改变
正在运行的容器：

```bash
RT() { docker exec xxj-runtime-fleet python "/fleet/$1" "${@:2}"; }

# 1) 容器里的包是哪个版本（磁盘上，随镜像走）
docker exec xxj-runtime-fleet python -c "import companion_runtime; print(companion_runtime.__version__)"

# 2) 某个 Runtime 进程自己报的（端口从 `RT fleet_admin.py list` 拿）
docker exec xxj-runtime-fleet python -c "
import json, urllib.request
d = json.load(urllib.request.urlopen('http://127.0.0.1:8787/health', timeout=20))
print('runtime_version =', d['runtime_version'])
print('state_version   =', d['state_version'])
"
```

看 `runtime_version`（包版本）。**别和 `state_version` 搞混**：后者是状态计数器，一直在涨
（2026-10-07 线上实测：8787 是 97069、8788 是 97084，都报 `runtime_version = 0.4.0`）。
`/v1/events` 响应里那个同名的 `runtime_version` **也是这个计数器**——一个名字两种意思。

两个**有意**的偏差，写在这里免得被当成故障：

- 仓库里的号 2026-10-07 走到 `0.5.0`，但**线上容器仍然报 `0.4.0`**：那次只改了源码字面量，
  没有重建镜像、没有滚动重启（为一个显示字符串停 11 个进程不值当）。下次按 §6 升级时自然对齐。
- 兼容性**不由这个号决定**：插件↔Runtime 是 `RUNTIME_API_VERSION` / `PROTOCOL_VERSION`
  （当前都是 `"1"`），插件↔AstrBot 是 `astrbot_version: ">=4.28,<5"`。
  所以插件和 Runtime 不必同版本升级，同号只是让人一眼能对上"这套是一起发的"。

回滚点：两个仓库都打了 `v0.5.0`（此前**从无任何 tag**）。插件另有按 tag 打的 zip，
可直接用 AstrBot WebUI 的「安装插件」上传。
