# 「浪潮」决策引擎 M0 虚拟前端隔离事件

## 摘要

在切换真实 NapCat 到虚拟 OneBot 后，旧 12 用户 Runtime fleet 短暂保持运行。虚拟前端会对任意 `user_id` 的发送调用返回成功，因此旧 fleet 将虚拟确认错误写成真实用户送达事实。该问题在第一轮虚拟端到端验证时发现并立即阻断。

## 影响

切换窗口内确认的真实用户污染：

- `1504838868`：一条虚拟确认的主动发送、对应 exposure、四个 pending label、raw events、attempt/runtime 状态。
- `1070754640`：只有切换前真实 exposure 的正常到期 label 结算，不属于虚拟发送污染。
- `20001`：模拟号数据，不属于真实用户污染。

没有 QQ 用户收到上述虚拟消息；问题是 Runtime 把模拟 ack 当成真实交付事实。

## 处置

1. 立即停止 `xxj-runtime-fleet`，NapCat 继续保持停止。
2. 在任何破坏性恢复前创建污染现场取证 dump：
   `/home/bomomo/tmp_backups/langchao-virtual-contamination-20261001-213006`
3. 使用切换前已校验的 PostgreSQL 全库备份：
   `/home/bomomo/tmp_backups/langchao-pre-rebuild-pg-20261001-210135/runtime-v2-all.dump`
4. 逐 schema 恢复 11 个真实用户；不恢复模拟号 schema，不改全局对象。
5. 将测试环境改为：
   - 独立 PostgreSQL `xxj-runtime-postgres-langchao-test`；
   - 独立 Runtime `xxj-runtime-langchao-test`；
   - 独立数据卷；
   - people 文件仅含 `default:FriendMessage:20001`；
   - 原 12 用户 fleet 持续停止。
6. 验证虚拟 OneBot → AstrBot → 单用户测试 Runtime → 回复闭环。

## 新增不变量

1. 虚拟 OneBot 上线前，所有包含真实 scope 的 Runtime 必须停止或从路由表移除。
2. 虚拟前端不得与真实用户数据库共享 exposure/label/attempt 写入权。
3. 测试 Runtime 使用独立 PostgreSQL、独立 schema/卷和只包含模拟号的路由表。
4. 切换脚本必须先断开发送方，再验证真实 fleet 停止，最后启动模拟前端；不得只切换 OneBot 客户端。
5. 虚拟发送成功不能作为真实用户送达事实迁移或训练证据。
6. 在任何真实/虚拟切换后，先审计新 exposure、attempt、raw event 和 label，再开始功能测试。

## 验收要求

后续自动化测试必须覆盖：

- 模拟路由表不出现真实用户 scope；
- 真实 fleet 与虚拟 OneBot 不同时处于可发送状态；
- 模拟 ack 只能写入模拟数据库；
- 真实 schema 在虚拟测试期间的送达事实计数不变化；
- 切换中断时默认保持两侧都不可发送，而不是恢复到双写状态。
