## 必须补的

按对"长期连续性"这一目标的影响排序，每条给出最小下一步。

1. **用户模型的时间性：基线判断（§29）+ 真正按 Δt 的漂移（§28）。** 现在"用户平常 8 小时回、今天 2 小时回"这种相对信号学不到（绝对阈值），而"很久没交互 → 旧认识该变虚"也不会发生（漂移只在新观察时跑）。最小下一步：给 `InteractionObservation` 存该用户 `reply_delay` 的指数均值基线，在 `user_model.py::_target_rewards` 里改用 z 分数；同时把 `UserModel._apply_drift` 拆出一个吃 `dt_seconds` 的 `tick_drift(dt)`，由 `runtime.py::Runtime._apply_time_passage` 调用。
2. **话题维度的分层（§25 / §1 目标4）。** `δ_话题`（以及可选的 `δ_时间`）不存在，导致"哪些话题容易聊起来"永久缺失，"晚上 11 点聊 AI 哲学样本太少"时无法只回退一层。最小下一步：在 `UserInteractionModel` 里加一个与 `_delta` 同结构的 `_topic_delta`（键取候选 `target` / 记忆 `topics` 首选），在 `_theta_for` 里相加，`_update` 里以更低步长学习。
3. **"没回复"这条证据没人产生（§22.3）。** 观察只能由用户下次开口或宿主上报触发，仓库里的 AstrBot 插件从不调用 `/observations`、`/delivery`，所以"主动后石沉大海"永远不会进入 `no_reply_weight=0.06` 那条路径，模型只从"有回复"的样本里学习。最小下一步：在 `endogenous_round`（或 `lazy_tick`）里对"已 sent、超过 N 小时、无 `interaction_observations`"的 attempt 生成 `BehaviourReaction(replied=False, reply_delay_seconds=...)` 观察。
4. **重估 / 冲突的消费端（§2.5、§18）。** `reappraisals`、`interpretation_versions.supersedes_id`、`memories.structured["supersedes"]`、`superseded_by_hint` 目前全是只写不读，"后来想明白了"和"以前不喜欢现在喜欢"都不会再影响任何一轮。最小下一步：在 `context.py::render_block` 增加一段"当时…现在…"（读最新一条 `interpretations.latest` + 它 supersede 的旧解释），并让 `_apply_reinterpretation` 追加一条 `EventType.REAPPRAISAL` 原始事件，使 §5.1 的"内部重估事件"回到不可变日志。
5. **工作局势进入召回（§3 的 WS→RAG、§20）。** 现在内部召回用最近 4 条原始事件当 query，`situation` 项是 lexical 的复制。最小下一步：给 `memory.py::RetrievalCue` 加 `situation_terms`，由 `projections.situation.list_active()` 的 content 填充，并在 `MemoryStore.retrieve` 里独立加权（替换 `0.25 × lexical` 的伪局势项）。
6. **情绪的用户模型归因（§8.1、§10）。** 入口路径算出的 `busy` 只影响工作局势推断，不影响情绪强度；带 attribution damping 的代码在无调用方的 `emotion.py::appraise_event` 里。最小下一步：给 `emotion.py::apply_new_emotion_events` 加 `attribution_damping: float = 1.0`，把 `runtime.py` 里 `busy` 的现值传进去，负向事件的 `impact` 乘 `(1 − 0.55×busy)`。
7. **冷启动安全探索的真实门控（§31）。** 六条条件目前只有两条是 prompt 文案，`cold_start` 与三个相关配置没人读。最小下一步：在 `motivation.py::decide` 里对 `prediction.cold_start` 的候选强制"长度上限 + 非 follow_up"门控（不满足则 `blocked`，reason=`cold_start_unsafe_probe`），把 `cold_start_prior_mean/precision` 接到 `DEFAULT_THETA` 的冷启动先验上或直接删掉。
8. **未尽之事状态机的两个不可达终态（§13.1）。** 用户说"算了别提了"这类撤回没有任何路径 —— 只能等过期。最小下一步：`unfinished.py` 增加 `cancel(...)`（或在 `detect_resolution` 里识别撤回语），并给 `POST /unfinished/{id}` 暴露该动作。
9. **工具结果进不可变日志（§5.1）。** 类型、评价分支（`emotion.py::appraise_event` 里的 `TOOL_RESULT` 处理）都在，但没有任何生产者。最小下一步：宿主插件在工具调用结束后 POST 一条 `tool_result`（通用 `POST /events` 已接受任意 `event_type`）。

## 可以永远不做的

1. **本地 2B 的两项职责（§2.1A / §8 / §11）与配套的解释缓存阈值（§12 的 `should_re_explain`、`task.emotion_explain_change_threshold`）。** 补丁 §16/§33 已正式废弃；`emotion.py::appraise_event`、`should_re_explain`、`emotion_explain_threshold`、`EmotionExplainer.explain_and_store` 这几处死代码建议**删除**而不是补接线 —— 接线等于把"每轮先让一个小模型评价再演出"这条被否决的路径恢复回来。
2. **`MemoryStatus.LOW_ACTIVATION` 中间档（§19）。** 归档判据（激活值 + 冷却天数）已经够用，补一个"低激活"状态只会多一个需要维护却无人观察的转移。
3. **§23 / §30 里那种"命名慢变量 + 单点置信度"（"主动交流接受度 +0.71 / confidence .86"）。** 特征×目标的权重矩阵 + 对角精度已经表达了同一信息；再造一层标量映射只会引入两套数值的同步问题。
4. **把当前一轮的 char/user 原文塞回解释器输入（§11.1 的 `event` 字段）。** 补丁 §4.1/§14.1 明确要求解释器只讲"进入本轮之前的长期底色"，加回去就是恢复被删的路径。
5. **§26 的 `min_weight` 权重下限。** 四因子乘积已经在 (0,1]，且 `no_reply_weight=0.06` 已经把最弱证据压得足够低；再加下限只会让弱证据变强。
6. **§13.3 之外的外源唤醒（外部日历 / 提醒 / 闹钟）。** 设计文档 §0 与补丁 §13 自己把它排除在"内源主动"之外，`scheduler.py` 现有的七类锚点已经覆盖内源唤醒。

## 审计中发现的实际缺陷

只报告，不修改。

1. **`emotion.py::appraise_event` 无任何生产调用方**（只有 `tests/test_emotion_boundaries_unfinished.py`）。它承载的价值观敏感度、`user_busy_probability` 归因、`TOOL_RESULT`/`BOUNDARY_*`/`ASSISTANT_MESSAGE` 分类在真实路径上都不存在 —— 入口走 `semantic.settlement_to_evaluation`。代码看起来"价值观影响情绪"，实际只有衰减率一项生效。
2. **`emotion.py::EmotionExplainer.should_re_explain` + `config.py::TaskConfig.emotion_explain_change_threshold`（0.12）双双无调用方**：文档化的"变化明显才重新解释"阈值没有生效，实际判据是把心境/冲动/节制四舍五入到 0.1 后拼字符串比相等（0.05 级的变化完全不触发）。
3. **`emotion.py::EmotionExplainer.explain_and_store` 无生产调用方**：解释缓存的写入实际只发生在 `reducer.py::Reducer._apply_explanation` / `_apply_interpretation_cache`（proposal 路径），`context.py::runtime_explanation` 只读不写。默认部署（`DisabledProvider`）下模板解释**每轮重算、从不入缓存**。
4. **`config.py` 有 17 个字段没有任何读者**（全仓 grep，排除 config.py 自身）：`cold_start_prior_mean`、`cold_start_prior_precision`、`downside_quantile`、`default_reply_delay_seconds`、`max_active_emotion_events`、`min_weight`、`emotion_explain_change_threshold`、`utility_epsilon`、`scan_recent_events`、`default_temporal_hours`、`unfinished_relevance_weight`、`commit_grace_seconds`、`max_committed_attempts`、`merge_window_seconds`、`max_observations_in_memory`、`render_timeout_seconds`、`request_timeout_seconds`。其中 §31（冷启动）、§22.3（默认回复延迟）、§9（活跃情绪上限）、§26（权重下限）四条直接让文档承诺的旋钮变成摆设：改这些值不会有任何行为变化。
5. **`memories.structured["supersedes"]` / `["superseded_by_hint"]` / `["superseded_at"]` 只写不读**（`memory.py::_find_conflicts`、`memory.py::consolidate`）。
6. **`typing.py::MemoryStatus.LOW_ACTIVATION` 没有任何赋值点**，只被 `memory.py:414` 当查询条件；记忆状态实际只有 `active`/`archived` 两态。
7. **`typing.py::UnfinishedStatus.CANCELLED` / `INVALIDATED` 没有任何赋值点**，只出现在只读集合里（`unfinished.py::SETTLED_MATTER_STATUSES`、`next_due_at` 与 `priority_of` 的过滤集）。`SETTLED_MATTER_STATUSES` 的注释把 `cancelled` 解释为"用户自己关掉了这件事"，但没有任何代码路径能产生它 —— 注释描述了一个不存在的分支。
8. **`typing.py::EventType` 里 `REAPPRAISAL`、`TOOL_RESULT`、`EMOTION_EVENT_EVAL`、`MEMORY_CONSOLIDATED`、`TICK` 在本仓没有任何生产者**。前两个尤其值得注意：§2.5/§5.1 要求"内部重估事件"进不可变日志，实际落在 `reappraisals` 表；§5.1 要求"工具结果"进日志，实际只有通用 `POST /events` 的口头支持，宿主插件`report_assistant_messages` 只上报 assistant 消息。
9. **`runtime.py::Runtime._action_spec` 返回的 `"length"` 键没有任何读者**：`user_model.FEATURE_NAMES` 里没有长度特征，`extract_features` 也不读它 —— 消息长度对用户模型预测零影响，但代码看起来"已经采集了长度"。
10. **`runtime.py::Runtime._situation_context` 的 `novelty` 恒为常量 0.6**、`local_hour` 采了但不映射到特征：`novelty` 这个特征列永远是同一个值（学不出东西），而"当前时间"作为 §22.2 要求的情境维度实际没有进模型。
11. **同一行为在"预测"和"观察"两条路径上被编码成不同的特征向量**：决策用 `runtime.py::Runtime._action_spec`（`question` = 类型属于 follow_up/curious_question/check_in，另有 `emotional_expression`/`topic_shift`），反馈用 `runtime.py::Runtime.observe_reply` 里内联的另一份 `action_spec`（`question` = 意图文本里有没有 `?`，没有 `topic_shift`）。`user_model.py::_update` 因此把权重学在一套与预测时不同的 x 上。
12. **`memory.py::_find_duplicate` 有一段重复语句**：`overlap = len(topics & set(memory.topics))` 与随后的 `if not overlap: continue` 连续出现两次（`memory.py:421-426`），第二份是死代码；同一处的判据 `ratio >= DEDUPE_EXACT_RATIO or ratio >= DEDUPE_TOPIC_RATIO` 因为 0.85 > 0.6 而**恒等价于 `ratio >= 0.6`**，`DEDUPE_EXACT_RATIO` 这个"完全相同事实"的档位实际不存在。
13. **`context.py::build_situation` 的 docstring 与返回键不符**：docstring 写"Returns: A mapping with `facts`, `inferences`, `active_items` and `unfinished`"，实现只返回 `facts`/`inferences`/`unfinished`/`generated_at` —— 没有 `active_items`。
14. **`memory.py::MemoryStore.tick_activation`、`memory.py::pool_times`、`memory.py::needs_consolidation`、`semantic.py::resolve_backlog` 四个模块级函数没有生产调用方**（前两个连测试都没有）：`tick_activation` 与真正在跑的 `decay_pool` 是两套并行实现，`needs_consolidation` 的判据被 `scheduler.py::_maintenance_due` 重新写了一遍，`resolve_backlog` 的策略被 `deep_refresh` 侧的 `unresolved_max_age_hours` 另写了一遍。
15. **宿主插件从不调用 `/observations` 与 `/delivery`**（`astrbot_plugin_companion_runtime/` 全目录 grep 无命中）：`Runtime.observe_reply` 的 `reaction` 参数、`BehaviourReaction.replied=False`、`explicit_positive/negative` 这些通道在随仓库发布的宿主里没有任何填写者，只能靠"用户下次开口"被 Runtime 自己推断出"有回复"的那一半。
