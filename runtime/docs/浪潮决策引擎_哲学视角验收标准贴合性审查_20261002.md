# 「浪潮」决策引擎：哲学视角验收标准贴合性审查

- 被审文件：`我即浪潮_马克思主义哲学视角_设计与收益目的审查要求_v1.0.md`
- 文件 SHA-256：`ab18f75fe9d8b6d2ace91e8736a7a5dd2b01b9144bae99a3538f58386dce4161`
- 对照实现：`feat/langchao-decision-engine`，schema v20
- 结论用途：审查验收标准本身，不授权上线

## 1. 总结论

该标准**总体贴合项目实际，而且方向是对的**。它最有价值的地方不是“马克思主义”术语本身，而是把项目最容易遗漏的三件事分开：

1. 契约与计算是否正确；
2. 被奖励的变化是否仍值得追求；
3. 真实效果是否有相应等级的证据。

它同时用 AGY-01—AGY-05 防止安全审查把系统改造成恒定沉默策略，这与当前「浪潮」的 external candidate + internal rest 竞争设计高度一致。

但本文件目前更接近**审查框架／测试目录**，还不是可以直接执行并据此给出“通过”的最终验收规范。主要缺口是：若干条款缺少可计算的 fixture、oracle、观察窗、容差、样本单位和阶段适用性；语义与真实效果项不能自动化成硬门禁；32 项场景还没有绑定当前仓库的具体入口和证据字段。

建议判定：

- 作为设计审查规范：**通过，可采用**；
- 作为隔离实现测试目录：**通过但需工程化**；
- 作为影子／真实灰度的唯一放行标准：**证据不足，需补运行协议**；
- 作为运行时奖励、用户画像或“哲学一致性分”：**明确禁止，文件本身也正确禁止了这一点**。

## 2. 与当前实现高度贴合的部分

### 2.1 证据分层和阶段结论

D/C/T/R/S/I 分类、未执行不得写通过、设计／实现／效果分别报告，与当前工程的真实情况完全贴合。例如：

- 契约、schema、CAS、数值核已有 C/T；
- 模拟号 shadow/live rest canary 有 T；
- 生产 B2 replay 只是 persisted audit replay，不能写成 pure assess 或真实效果；
- 用户体验改善目前没有 R/S，必须保持“未验证”。

### 2.2 目的—指标登记卡

PUR-01—PUR-12 是本文件最适合项目的部分。当前 reward compiler 已经把 reply、continuation、negative、delivery 和模板内在结果拆开，也明确不使用 legacy `internal_utility` 作为最终收益；但“为什么 reply 值得计价、在哪些场景不相关”仍应登记，而不能因为公式正确就跳过目的审查。

### 2.3 现实条件与未知保留

MAT-01—MAT-05 对应现有：来源引用、scope FK、unknown forecast=`None`、能力/权限 envelope、社会记忆 source hash。尤其 MAT-02 与当前 unavailable prediction 不补 False 的规则直接一致。

### 2.4 实践和结果分账

PRA-01—PRA-06 对应现有 attempt/render/send/ack、v19 live commit、OutcomeToken 和 terminal settlement。对抗审计刚发现并修复的 render→send engine 丢失问题，正是 PRA-01/PRA-02 的典型实现偏离。

### 2.5 历史性与依赖失效

HIS-01—HIS-06 与 event cursor、真实 elapsed time、revision、social dependency invalidation、tombstone、解释 supersedes、working-set 变化开新 round 一致。

### 2.6 反向主体性验收

AGY-01—AGY-05 非常必要。当前模拟 live canary 只有 internal rest 合格，没有 external candidate 越阈值；若只看零违规会误判成功。该标准正确要求同时证明普通表达／探索路径可达。

## 3. 需要修订才能成为可执行验收的地方

### 3.1 32 项是场景目录，不是测试定义

每个 T 项还需补：

- fixture 的 canonical JSON；
- 初始数据库状态和 scope；
- 固定 config/hash；
- 时间轴与 `as_of`；
- 允许的输出集合；
- hard invariant 与 semantic rubric 分离；
- 数值容差和最大步数；
- 样本单位（事件、goal episode、attempt 或用户）；
- 证据文件位置和隐私保留期限。

没有这些内容，两个审核者可以用不同输入都声称执行了 T24 或 T29。

### 3.2 不要把语义项伪装成确定性单测

T01、T04、T06、T07、T09、T13、T17、T18、T21—T28、T31、T32 含语义成分。它们应拆成：

- 机械部分：身份、scope、来源、能力、结算、权限、时间；
- 语义部分：人工小样本／经校准评审，保留原文、rubric、争议和一致率。

禁词表、单个 Judge 或字符串匹配不能代替语义验收。

### 3.3 “应形成决定”不能没有时间和配方

AGY-01、T11、T23、T24、T29、T32 涉及可达性和终止。必须冻结：

- LangchaoParameters；
- decision budget；
- initial readiness；
- attraction/value/attention；
- elapsed time序列；
- tie order；
- permission/boundary version。

否则“没有决定”既可能是 bug，也可能只是给定预算下正确 defer。

### 3.4 阶段门禁需要 machine-readable manifest

建议增加 `acceptance-manifest-v1.json`：

- commit、schema version、config hash；
- 适用 T 项；
- fixture hash；
- expected invariant；
- evidence class；
- status；
- blocker；
- reviewer；
- 生成时间。

报告 Markdown 用于解释，manifest 用于防止漏项和静默改尺子。

### 3.5 目的审查不能每轮运行

文件已正确写明这一点，工程上应进一步规定触发条件：reward template、目标创建规则、训练标签、评审 prompt、自动调参目标或发布阶段变化时重审；普通 scheduler wake 不调用“哲学评委”。

### 3.6 真实效果不能由模拟代替

T30—T32 与影子对照只能证明选择差异、可达性和不变量，不能证明用户满意、关系改善或“更有主体性”。真实效果必须在单独授权的有限灰度中评估；当前用户明确不上线，因此状态只能是未执行。

## 4. 当前 32 项按可执行性分类

### 4.1 可直接自动化为硬断言

T02、T03、T05、T08、T10、T12、T14、T15、T16、T19、T20、T29 的机械部分。

其中当前已有较强覆盖：scope 隔离、unknown forecast、OutcomeToken 幂等、权限优先、送达未知不盲重发、时间推进、state restart/CAS、tombstone/invalidation、数值有界与 defer。

### 4.2 可自动化，但需先补 fixture/oracle

T01、T04、T11、T18、T21、T23、T24、T26、T27、T30、T32。

这些需要固定事实、参数、候选供给、预算和允许结果集合；不能仅断言“发了／没发”。

### 4.3 必须混合人工语义评审

T06、T07、T09、T13、T17、T22、T25、T28、T31，以及 T01/T04/T18/T21/T23/T24/T27/T32 的语义部分。

### 4.4 当前不适合作为上线前自动硬门禁

- “更有意义”“更有主体性”“关系更好”等总体效果；
- 对隐藏世界设定的猜中率；
- 单一综合道德分；
- 固定联系率／回复率；
- 未经真实暴露却要求用户满意提升。

它们可以作为研究问题或真实灰度指标，但不能在离线阶段伪装成已验证结论。

## 6. 建议的最小修订

1. 保留哲学六视角作为章节组织，不加入运行时分数。
2. 给 MAT/PRA/CON/HIS/PUR/VER/AGY 每条增加“适用阶段”。
3. 将 T01—T32 拆成 `mechanical_assertions` 与 `semantic_review` 两栏。
4. 每个数值场景增加 frozen parameters、timeline、budget、tolerance。
5. 增加 machine-readable acceptance manifest 与 fixture hashes。
6. 将“通过”统一写成“通过（限版本／fixture／证据类型）”。
7. 增加一条专门验证 render→send→ACK 引擎 provenance 的结构场景；该问题已在本轮真实对抗审计中出现。
8. 增加一条 live commit 必须精确 FK 到 dispatch claim 的结构场景。
9. 增加一条“无 shadow witness 时 coverage=0，不得把无暴露写成0%违规”的报告场景。
10. 将 T30 的四组对照细化为候选供给、节奏、引擎、语义生成四因素，而不是仅列版本名称。

## 7. 最终判定

你的标准不是空泛哲学包装，核心内容与当前工程风险高度贴合，尤其是目的审查、证据等级、反向主体性和不做综合分这四点。它可以作为正式审查基线。

但若问“现在能否直接拿它宣布验收通过”，答案是不能。应先把 32 项工程化成固定 fixture、机械 oracle、语义 rubric、阶段 manifest，并承认当前 external live 黑盒与 11 用户 pure-assess replay 证据仍不足。

因此建议状态：**审查标准本身通过（需工程化修订）；当前「浪潮」实现仍不批准上线。**
